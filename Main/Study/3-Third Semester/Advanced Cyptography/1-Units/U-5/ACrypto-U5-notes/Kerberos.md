# Kerberos

## Definition

**Kerberos** is a **network authentication protocol** that uses a **trusted third party**, called the **Key Distribution Center (KDC)**, to authenticate users and provide secure communication over an insecure network.

It was developed at **MIT (Massachusetts Institute of Technology)** and is based on **symmetric key cryptography**.

---

# Why Kerberos is Needed

Suppose Alice wants to access a file server.

Without Kerberos:

* Alice may have to send her password to every server.
* An attacker could steal the password.

With Kerberos:

* Alice authenticates **once** with the KDC.
* The KDC issues **tickets**.
* Alice uses the tickets to access different services.
* Her password is **never sent to the service server**.

---

# Components of Kerberos

1. **Client (User)**

   * The user requesting a service.

2. **Authentication Server (AS)**

   * Verifies the user's identity.

3. **Ticket Granting Server (TGS)**

   * Issues tickets for accessing services.

4. **Service Server (SS)**

   * The server providing the requested service.

5. **Key Distribution Center (KDC)**

   * Consists of:

     * Authentication Server (AS)
     * Ticket Granting Server (TGS)

---

# Kerberos Architecture

```text
          +-------------------------+
          | Key Distribution Center |
          |                         |
          |  +------+   +------+    |
Client --->|  |  AS  |-->| TGS |----> Service Server
          |  +------+   +------+    |
          +-------------------------+
```

# Kerberos Protocol (Step-by-Step Explanation)

## Symbols Used

| Symbol      | Meaning                                                |
| ----------- | ------------------------------------------------------ |
| $C$         | Client (User)                                          |
| $AS$        | Authentication Server                                  |
| $TGS$       | Ticket Granting Server                                 |
| $S$         | Service Server                                         |
| $KDC$       | Key Distribution Center (AS + TGS)                     |
| $K_C$       | Client's secret key (derived from the user's password) |
| $K_{TGS}$   | Secret key of the Ticket Granting Server               |
| $K_S$       | Secret key of the Service Server                       |
| $K_{C,TGS}$ | Session key shared between Client and TGS              |
| $K_{C,S}$   | Session key shared between Client and Service Server   |
| $TS$        | Timestamp                                              |
| $Lifetime$  | Validity period of the ticket                          |
| $TGT$       | Ticket Granting Ticket                                 |
| $Ticket_S$  | Service Ticket                                         |
| $E(K,X)$    | Encrypt message $X$ using key $K$                      |

---

# Step 1: Client → Authentication Server

$$
\text{ID}_C \parallel \text{ID}_{TGS} \parallel TS_1
$$

### Meaning of each field

* $\text{ID}_C$ → Identity (username) of the client.
* $\text{ID}_{TGS}$ → Identity of the Ticket Granting Server.
* $TS_1$ → Current timestamp generated by the client.

### Why send this?

The client is saying:

> "I am Client C. I want to communicate with the Ticket Granting Server. Here is my current timestamp."

The timestamp helps prevent replay attacks.

---

# Step 2: Authentication Server → Client

$$
E(K_C,[K_{C,TGS} \parallel TGT])
$$

Inside the encrypted message:

$$
K_{C,TGS}
$$

* A newly generated **session key**.
* Used only between the Client and the TGS.

and

$$
TGT
===

E(K_{TGS},
[K_{C,TGS}
\parallel
\text{ID}_C
\parallel
TS
\parallel
Lifetime])
$$

### Meaning of each field

* $K_{TGS}$ → Secret key known only by the TGS.
* $K_{C,TGS}$ → Session key between Client and TGS.
* $\text{ID}_C$ → Client's identity.
* $TS$ → Ticket creation time.
* $Lifetime$ → Ticket expiration time.

### Why encrypt the TGT with $K_{TGS}$?

Only the TGS knows $K_{TGS}$.

Therefore,

* Client **cannot modify** the ticket.
* Attacker **cannot read** the ticket.
* Only the TGS can open it.

---

# Step 3: Client → Ticket Granting Server

The client sends

$$
TGT
\parallel
E(K_{C,TGS},
[\text{ID}_{Service}
\parallel
TS_2])
$$

### First Part

$$
TGT
$$

This is the ticket received from the Authentication Server.

It proves that the client has already been authenticated.

---

### Second Part

$$
E(K_{C,TGS},
[\text{ID}_{Service}
\parallel
TS_2])
$$

Meaning:

* $\text{ID}_{Service}$ → The service the client wants (e.g., File Server, Email Server).
* $TS_2$ → New timestamp generated by the client.

Encrypted using

$$
K_{C,TGS}
$$

which only the Client and TGS know.

### Why send this?

The client says:

> "I already have a valid Ticket Granting Ticket. Please give me a ticket for this service."

---

# Step 4: TGS → Client

The TGS sends

$$
E(K_{C,TGS},
[K_{C,S}
\parallel
Ticket_S])
$$

Inside,

$$
K_{C,S}
$$

* Session key between Client and Service Server.

and

$$
Ticket_S
========

E(K_S,
[K_{C,S}
\parallel
\text{ID}_C
\parallel
TS
\parallel
Lifetime])
$$

### Meaning of each field

* $K_S$ → Secret key of the Service Server.
* $K_{C,S}$ → Session key for communication with the service.
* $\text{ID}_C$ → Client identity.
* $TS$ → Ticket creation time.
* $Lifetime$ → Ticket validity period.

Only the Service Server can decrypt this ticket.

---

# Step 5: Client → Service Server

The client sends

$$
Ticket_S
\parallel
E(K_{C,S},
[\text{ID}_C
\parallel
TS_3])
$$

### First Part

$$
Ticket_S
$$

The service ticket received from the TGS.

---

### Second Part

$$
E(K_{C,S},
[\text{ID}_C
\parallel
TS_3])
$$

Meaning:

* $\text{ID}_C$ → Client identity.
* $TS_3$ → Fresh timestamp.

Encrypted using

$$
K_{C,S}
$$

### Why send this?

The Service Server verifies that

* the client owns the session key,
* the request is fresh,
* the ticket has not expired.

---

# Step 6: Service Server → Client

The Service Server replies

$$
E(K_{C,S},
TS_3+1)
$$

### Meaning

* The server decrypts the client's message.
* It increments the timestamp by 1.
* It encrypts it again using $K_{C,S}$.

### Why send $TS_3+1$?

This proves that:

* the server successfully decrypted the client's message,
* the server knows the session key $K_{C,S}$.

The client also verifies the response.

Thus, **mutual authentication** is completed.

---

# Overall Flow

```text
Client
   │
   │ Request TGT
   ▼
Authentication Server
   │
   │ Gives TGT + Session Key (KCTGS)
   ▼
Client
   │
   │ Sends TGT and requests Service Ticket
   ▼
Ticket Granting Server
   │
   │ Gives Service Ticket + Session Key (KCS)
   ▼
Client
   │
   │ Sends Service Ticket
   ▼
Service Server
   │
   │ Returns TS3+1
   ▼
Secure Communication Starts
```

---

## Easy Way to Remember

* **Step 1–2:** Get a **Ticket Granting Ticket (TGT)** from the **Authentication Server (AS)**.
* **Step 3–4:** Use the **TGT** to get a **Service Ticket** from the **Ticket Granting Server (TGS)**.
* **Step 5–6:** Use the **Service Ticket** to access the **Service Server (S)** and complete **mutual authentication**.

This **AS → TGS → Service Server** flow is the key idea behind Kerberos and is commonly expected in exams.

---

# Advantages

* Password is never sent over the network.
* Provides mutual authentication.
* Prevents replay attacks using timestamps.
* Supports Single Sign-On (SSO).
* Uses temporary session keys.

---

# Disadvantages

* Requires synchronized clocks.
* KDC is a single point of failure.
* If the KDC is compromised, the entire system is affected.

---

# Applications

* Windows Active Directory
* Enterprise networks
* UNIX/Linux authentication
* Single Sign-On (SSO)

# 5-Mark Exam Answer

**Kerberos** is a network authentication protocol based on **symmetric key cryptography**. It uses a **Key Distribution Center (KDC)**, consisting of an **Authentication Server (AS)** and a **Ticket Granting Server (TGS)**, to authenticate users and issue tickets for accessing network services. A client first obtains a **Ticket Granting Ticket (TGT)** from the AS, then uses it to obtain a **Service Ticket** from the TGS. The Service Ticket is presented to the Service Server, which verifies it and establishes a secure session using a shared session key.

**Advantages:**

* Mutual authentication
* Password is never sent over the network
* Prevents replay attacks
* Supports Single Sign-On (SSO)

**Disadvantages:**

* Requires synchronized clocks
* KDC is a single point of failure
* Depends on the security of the KDC
